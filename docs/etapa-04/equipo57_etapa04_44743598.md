#### 🚀 Aporte Realizado
1. Diseño de consulta SQL con `INNER JOIN` (VENTA, CONTIENE, PRENDA, CATEGORIA) para consolidar transacciones.
2. Uso de funciones de agregación (`COUNT`, `SUM`, `GROUP BY`) para calcular la cantidad de comprobantes, prendas vendidas y recaudación por categoría.
3. **Redacción y estructuración de los Casos de Uso, definiendo los escenarios operativos y analíticos que justifican el valor de negocio de cada consulta.**

#### ⚠️ Problemas o dificultades identificadas
1. **Unidades vs. Registros:** Diferenciar el recuento de filas (`COUNT`) de la cantidad real de prendas vendidas.
2. **Precios dinámicos:** Evitar que cambios futuros en el precio de las prendas alteren el cálculo de la recaudación histórica.
3. **Filtro de fechas:** Ajustar el uso de `BETWEEN` en campos `DATETIME` para no excluir las últimas horas del día.
4. **Sintaxis DDL:** Mantener consistencia estricta de nombres y alias con el script oficial.

#### 💡 Soluciones o propuestas realizadas
1. Se aplicó `COUNT(DISTINCT v.Nro_Comprobante)` para comprobantes únicos y `SUM(co.Cantidad)` para unidades totales.
2. Se multiplicó la cantidad por `co.Precio_Historico` (tabla intermedia) en lugar del precio actual, asegurando integridad financiera.
3. Se ajustó el límite final del filtro temporal a `2026-10-14 23:59:59`.
4. Se revisó el código SQL contra el modelo físico para garantizar compatibilidad.
