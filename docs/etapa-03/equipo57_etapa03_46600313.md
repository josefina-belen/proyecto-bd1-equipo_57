## Aporte realizado

- **Implementación del DDL de las tablas dependientes  (`VENTA` y `PRENDA`)** a partir del modelo relacional previamente normalizado.

- **Definición de Claves Primarias:**
  - En VENTA: `PK_V_Nro_Comprobante`, utilizando la propiedad IDENTITY(1,1).
  - En PRENDA: `PK_P_Codigo_SKU`, sobre el identificador único del producto.

- **Configuración de Claves Foráneas:**
  - `FK_VENTA_DNI`: asocia cada venta con el cliente  en la tabla `CLIENTE`.
  - `FK_PRENDA_ID_Categoria`: vincula cada prenda con su registro  en `CATEGORIA`.

- **Implementación de restricciones de validación de dominio:**
  - `CHK_VENTA_Fecha`: impide registrar ventas con fechas futuras respecto a `GETDATE()`.
  - `CHK_PRENDA_Stock`: garantiza que las existencias en inventario no sean negativas.
  - `CHK_PRENDA_Precio_Actual`: asegura que el valor de la prenda sea estrictamente positivo.

---

## Problemas o dificultades identificadas

- Determinar la configuración adecuada de las acciones referenciales (ON DELETE` y `ON UPDATE) entre las tablas independientes y dependientes.
- Definir las condiciones adecuadas para las restricciones CHECK.

---

## Soluciones

- Se analizó la regla de negocio transaccional y se estableció ON DELETE NO ACTION para evitar que la eliminación accidental de un cliente o categoría borre comprobantes e inventarios existentes.

- Se aplicó ON UPDATE CASCADE para que la actualización de un identificador en la tabla padre se propague a las ventas y prendas relacionadas.

- Se estructuraron las restricciones CHECK para validar la fecha de facturación y establecer comparaciones numéricas que permitan resguardar el stock y el precio actual.
